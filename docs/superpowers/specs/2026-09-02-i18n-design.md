# Multi-language support (i18n) — design

**Date:** 2026-09-02 · **Branch:** feat/i18n-foundation · **Status:** D1–D9 approved 2026-09-02; Wave 0 BUILT (PR #105); **Wave 1 BUILT 2026-09-02** (branch `feat/i18n-public`, stacked on #105; §4 amended for region detection); Waves 2–6 not started.

## 1. Goal

Booklo speaks one language today: English, hardcoded in JSX, in server-action
error strings, in email templates and in three copy modules (`vocab.ts`,
`booking-page/copy.ts`, `marketing/site.ts`). Dates are formatted with a
literal `"en-GB"` in ~45 files.

This programme adds **Ukrainian** (locale code `uk`, not `ua` — `ua` is the
country, `uk` is the language) as the first second language, with
infrastructure that makes the third language (Polish, later) a one-file job:

1. **One mechanism** for every surface: admin, public booking page, embed
   widget, token pages, emails, auth, marketing.
2. **Translations that read as native** — a glossary and style guide reviewed
   before any strings are written, then native review per wave.
3. **Guards that keep it that way**: a new hardcoded string, a missing key, a
   broken plural or a placeholder mismatch fails `npm run verify`.

### Not in scope (and why)

- The parked pipeline features (`programs`, `participants`, `chasing`,
  `templates`, `/p`, `/portal`) and the owner-only `/utils`, `/dev` surfaces.
  None are in the nav; they stay English until un-parked.
- A UAH currency. `CURRENCIES` is a Stripe Managed Payments whitelist; UAH
  settlement is a billing decision, not an i18n one.
- Translating provider-authored content (service names, descriptions, page
  sections). That is the org's own copy in whatever language they write it.

## 2. Decisions (recommended; each is reversible until Wave 0 lands)

| # | Decision | Why | Alternative rejected |
|---|---|---|---|
| D1 | **`next-intl` 4.x, "without i18n routing" mode.** | Next 16 peer support, ICU plurals/select (Ukrainian has four plural forms), typed message keys, `getTranslations` in server actions and email builders, `useFormatter` for locale-aware dates. One dependency replaces ~300 lines of interpolation, plural and typing code we would otherwise own. | Hand-rolled dictionaries + React context: zero deps, but plurals, rich text and typed keys have to be rebuilt and taught; JSON that translation tools consume is still needed. |
| D2 | **Two locale axes.** *Interface locale* — per person (a staff member in the admin, a visitor on marketing/auth). *Org locale* — per org, governs everything the org's clients see and every email the org sends. | A Ukrainian salon has Ukrainian clients; its owner may still prefer the admin in English. Mixing the two axes into one setting gets one of those wrong. | One global per-org language: wrong for multi-staff orgs and for the marketing site, where there is no org. |
| D3 | **No URL prefixes.** `/<handle>`, `/embed/<handle>`, `/booking/<token>` and every admin route keep their addresses. Public surfaces accept a `?lang=` override (also carried by the embed snippet as `data-lang`). | The booking URL is a brand asset printed on cards and pasted into websites; the embed is an iframe on someone else's site; the admin is behind auth. A `[lang]` segment would 404 every existing link and gains nothing where there is no SEO. | `[lang]` routing: the Next.js guide's default; only marketing would benefit (see "Later" in §9). |
| D4 | **Emails follow the org locale** (client confirmations, reminders, approval mails, provider and staff notices). | The org chose the language its clients see; no per-booking locale exists yet. | Per-booking locale (`bookings.locale`): needs a visitor switcher first; listed under "Later". |
| D5 | **Supabase auth emails (confirm, reset, magic link) stay English until Wave 6**, which routes them through the `send_email` auth hook and our own transport. | Supabase's config holds one template per type; localising means rendering them ourselves. The user's locale is stored from Wave 0 on (`user_metadata.locale`), so Wave 6 has the data. | Two templates with both languages stacked: reads as spam, and does not scale. |
| D6 | **Terms and Privacy stay English** until Andrii approves a reviewed Ukrainian text. | Legal copy is not UI copy; a machine draft that is "mostly right" is a liability. | Translate inline with the marketing wave. |
| D7 | **Translation ownership:** Claude drafts `uk` strings against the glossary; Andrii (native speaker) reviews the glossary first, then each wave's `uk.json` diff before merge. | A glossary reviewed once prevents the same term being translated three ways across waves. | Outsourced translation: no context, and the glossary still has to exist. |
| D8 | **Missing `uk` key → English string at runtime, and a failing test at CI.** | A visitor never sees a raw key path; a developer never ships a gap. | next-intl's default (render the key path). |
| D9 | **Existing copy objects (`vocab.ts`, `STARTER`, `SITE`) become message namespaces**; the copy-guard tests (`FORBIDDEN_COPY`, no "skip") keep running, per locale. | They already isolate copy from components — half the work is done; only the storage changes. | Keep them as TS objects keyed by locale: loses ICU and typed keys. |

## 3. Architecture

```
messages/
  en.json                 source of truth, written by developers
  uk.json                 full translation (parity enforced)
  GLOSSARY.md             terms, tone, per-language notes (§7)
src/i18n/
  config.ts               LOCALES, DEFAULT_LOCALE, LOCALE_NAMES, isLocale, negotiateLocale
  cookie.ts               LOCALE_COOKIE name + options
  messages.ts             loadMessages(locale): en deep-merged under <locale> (D8)
  request.ts              next-intl getRequestConfig: requestLocale → cookie → Accept-Language → en
  actions.ts              setLocale(locale): cookie + user_metadata (signed-in) + revalidate
  locale-switcher.tsx     the one switcher component (Settings › Interface, auth pages)
src/types/next-intl.d.ts  AppConfig { Locale; Messages: typeof en.json } → typed keys
next.config.ts            wrapped in createNextIntlPlugin()
```

**Server components** call `getTranslations("ns")` / `getFormatter()`; **client
components** call `useTranslations("ns")` / `useFormatter()`; **server actions
and email builders** call `getTranslations({ locale, namespace })` with an
explicit locale (actions run outside the page render, so they resolve the
locale themselves — from the cookie for admin actions, from the org for public
actions). Each surface's layout wraps its tree in `NextIntlClientProvider`
(which inherits locale and messages from `request.ts`) and sets `lang` on its
wrapper element.

**The root layout is not touched until Wave 5.** Reading the cookie there
(`getLocale()`) would make every route dynamic, and the marketing pages are
statically prerendered today. The dashboard and auth pages already read
cookies, so their layouts carry the provider from Wave 0; `<html lang>` moves
from the literal `"en"` to the interface locale when Wave 5 decides how
marketing renders (cookie-dynamic, or `/uk` routes with `generateStaticParams`
for SEO — that choice is deferred to Wave 5 on purpose).

**Fallback (D8):** `loadMessages("uk")` returns `deepMerge(en, uk)`. A key
absent from `uk.json` renders English. The parity test (§6) makes that a CI
failure, so the merge is a safety net, never a workflow.

**Fonts:** Inter gains the `cyrillic` subset (root and marketing layouts).
Outfit (wordmark, marketing display headlines) has no Cyrillic — the wordmark
is Latin anyway; Ukrainian marketing headlines fall back to Inter via the
font stack, which is acceptable for Wave 5 and revisited if it looks wrong.
Geist Mono renders digits and times only. Widget fonts: Inter, Lora and IBM
Plex Mono cover Cyrillic; Geist, DM Sans and Space Grotesk do not — the
widget font picker shows a "Latin only" note next to those (Wave 4), and the
CSS stack behind each already falls back to system fonts.

## 4. Locale resolution per surface

| Surface | Locale | Resolved from | Switcher |
|---|---|---|---|
| Admin (`(dashboard)`, `/onboarding`) | interface | `NEXT_LOCALE` cookie; seeded from `user_metadata.locale` by the proxy when the cookie is missing; otherwise `Accept-Language` → `en` | Settings › Interface › Language |
| Auth pages | interface | cookie → `Accept-Language` → `en` | small switcher under the form; signup stores the choice in `user_metadata.locale` |
| Marketing (`/`, `/pricing`, `/waitlist`) | interface | cookie → `Accept-Language` → `en` | footer switcher |
| Hosted page `/<handle>`, `/<handle>/<staff>`, `/<handle>/spaces` | **org** | `orgs.locale`; `?lang=` overrides when valid | none in v1 (see Later) |
| Embed `/embed/<handle>` | **org** | `orgs.locale`; `?lang=` from the snippet's `data-lang` | none |
| Manage page `/booking/<token>` | **org** | the token's org | none |
| Emails the org sends | **org** | `orgs.locale` at send time | — |
| Auth emails (Supabase) | interface | `user_metadata.locale` (Wave 6) | — |
| `/utils`, `/dev`, parked pipeline pages | `en` | — | — |

**Amendment (Wave 1, 2026-09-02 — visitor region):** public surfaces resolve
`?lang=<valid>` → visitor country (Vercel's `x-vercel-ip-country`) in
`REGION_LOCALES` (`{ UA: "uk" }` — only countries whose language the product
speaks and where it is unambiguous; nothing maps to `en`, so an org's choice
is never overridden *towards* English) → `orgs.locale` → `en`
(`src/i18n/public-locale.ts`). Public server actions resolve the same
triple from the proxy's `x-pathname` (carries the query), the country header
and the org's locale, so an action error reads in the page's language. An
explicit `?lang=` travels with the cross-links and the manage link; a
region- or org-derived locale resolves the same way on the next page and
needs no query. The embed snippet's `data-lang` is dropped: `?lang=` on the
iframe `src` is the override. Emails still follow `org.locale` (D4).

**How the org locale reaches the render:** each public layout and page calls
`setRequestLocale(org.locale)` first (next-intl's per-request override, which
`request.ts` reads as `requestLocale`), renders a
`<NextIntlClientProvider locale={org.locale} timeZone={org.timezone}
messages={pick(messages, ["public", "common", "errors"])}>` around the tree,
and wraps the content in `<div lang={org.locale}>`. The `lang` attribute
scopes the language for screen readers on that subtree; the root `<html
lang>` stays the interface locale. Picking namespaces keeps the widget's
client bundle to the strings it uses.

**Public server actions** already load the org (`ctx.org`); they call
`getTranslations({ locale: org.locale, namespace: "errors" })` for any string
they return. Error constants (`GENERIC_WRITE_ERROR`, `TOO_MANY_REQUESTS`,
`SLOT_TAKEN`, the `slotLostMessage` rule) become keys under `errors.*` and are
resolved at the return site — never stored translated.

**Hydration rule (unchanged from the date-picker lesson):** the locale is
decided on the server and handed down; nothing reads `navigator.language`.
Server and client therefore always format with the same locale.

## 5. Message conventions

- **One JSON per locale**, top-level namespaces per surface: `common`
  (Save, Cancel, Close, Back, Delete, Loading…), `errors` (shared action
  errors), `auth`, `shell` (nav, ⌘K, user menu), `settings`, `overview`,
  `bookings`, `availability`, `services`, `spaces` (today's `SPACES` object),
  `appointments` (today's `APPOINTMENTS`), `team`, `clients`, `billing`,
  `onboarding`, `studio` (booking-page builder, today's `STARTER`), `embed`
  (Website embed settings), `public` (hosted page, widget, slot layouts,
  manage page, spaces flows), `emails`, `marketing` (today's `SITE`).
- **Keys are semantic, camelCase, nested by component**: `auth.login.title`,
  `errors.slotTaken`, `public.widget.nextAvailable.showMore`. Never the
  English sentence as the key.
- **ICU for everything dynamic**: `{count, plural, one {# слот} few {# слоти}
  many {# слотів} other {# слота}}`; `{channel, select, spaces {…} other {…}}`
  replaces functions like `bookingDescription(mode, orgName)`. No string
  concatenation, no `+ " "` — a sentence is one message.
- **Rich text** (a sentence containing a link) uses `t.rich("key", { link:
  (chunks) => <Link…>{chunks}</Link> })`.
- **Never translated**: "Booklo", plan names ("Free", "Pro"), language names
  in the switcher (`LOCALE_NAMES` shows each language in itself), handles,
  URLs, ISO codes.
- **Dates, times, money** go through `useFormatter()` / `getFormatter()` (or
  `Intl.*` with the current locale for the email builders). The `"en-GB"`
  literals are removed wave by wave. `formatWhenLine(starts, timeZone, locale)`
  gains the locale argument. `money.ts` formats with the UI locale and the org
  currency (`uk` + PLN → "120 zł" stays readable; `Intl` handles it).
- **Week starts Monday, 24-hour clock** — both already true and unchanged.

## 6. Guards (all run in `npm run verify`)

| Guard | Where | Fails when |
|---|---|---|
| Key parity | `src/i18n/messages.test.ts` | a key exists in one locale and not the other, or any value is empty |
| Placeholder parity | same | `{name}` in `en` but not in `uk` (or vice versa) |
| ICU syntax | same | a message does not compile (`intl-messageformat`, next-intl's own parser) |
| Plural completeness | same | a `plural` in `uk.json` lacks a category `Intl.PluralRules("uk").resolvedOptions().pluralCategories` requires (one/few/many/other). Derived per locale — no hand-kept list |
| Untranslated | same | a `uk` value equals its `en` value, unless the key is on the `SAME_IN_EVERY_LOCALE` allowlist (brand, codes, "OK") |
| Forbidden copy | existing `copy.test.ts` / `site.test.ts`, now looping over locales | "rental", "offering", "skip" (and their `uk` equivalents, listed in the glossary) appear in a message |
| Typed keys | `tsc` via `AppConfig.Messages` | `t("auth.login.titel")` |
| No new literals | `react/jsx-no-literals` (already shipped inside `eslint-config-next`) enabled per directory as each wave migrates it | a JSX text literal appears in a migrated directory |
| Layout | Playwright screenshots in `uk` at 1440 and 390 per wave | Ukrainian (≈25% longer) overflows a button, tab or nav item |

The lint rule is a **ratchet**: Wave 0 turns it on for `src/app/(auth)/**`
and `src/features/auth/**`; every later wave adds its directories. New code in
a migrated directory cannot regress.

Style: formal **ви**, lowercase in running text; command buttons use the
infinitive ("Зберегти", "Скасувати"), instructions and errors the
ви-imperative ("Оберіть", "Спробуйте"); no exclamation marks; sentence case; keep the
English rhythm (short, one idea per sentence); the forbidden list per locale
("оренда", "офер", "пропустити").

## 8. Data

- **`orgs.locale text not null default 'en'`**, migration **0069** (next free
  after 0068). CHECK is format-only (`^[a-z]{2,3}(-[A-Z]{2})?$`) so a new
  language never needs a migration; the app validates against `LOCALES`.
  Written only through `update_org_scheduling`, widened to five arguments
  (`p_locale`) with the 0058 drop-and-recreate pattern; `update_org_scheduling`
  is already how onboarding and the studio Settings tab write timezone and
  currency, so the Language field sits beside Timezone on the Booking page
  Settings tab (admin IA ruling: what clients see is configured under Booking
  page, not Settings). New orgs get the creator's interface locale.
- **`auth.users.user_metadata.locale`** — the person's interface locale. No
  migration: `supabase.auth.updateUser({ data: { locale } })` on switch,
  `options.data.locale` on signup. The proxy seeds the cookie from it when the
  cookie is missing, so the preference follows the user across devices.
- **Cookie `NEXT_LOCALE`**: `path=/`, one year, `SameSite=Lax`, `HttpOnly`
  (only the server reads it), `Secure` when the app URL is https.

## 10. Adding a language (the scalability check)

1. Add the code to `LOCALES` and its name to `LOCALE_NAMES` in
   `src/i18n/config.ts`; add one loader line in `src/i18n/messages.ts`.
2. Copy `messages/en.json` to `messages/<code>.json` and translate. The
   parity, plural and untranslated tests fail until it is complete — a
   partial locale cannot ship.
3. Add a glossary section and the forbidden-word list for the language.
4. Check font subsets (`Inter` covers Latin, Cyrillic, Greek, Vietnamese).
5. Run the Playwright screenshot pass in the new locale.
6. Auth email templates for the language (Wave 6 mechanism).

No migration, no routing change, no new component.
